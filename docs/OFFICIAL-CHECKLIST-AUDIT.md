## 1. Вердикт

ВЕРДИКТ: likely pass, плановый проход по чеклисту, оценочный счет 90-98 из 100 (не сертифицировано официальным жюри).

Реальный счет подтверждается только запуском официального жюри. Selbst-верификация `python -m letro.verify` (100/100) — это самостоятельная рубрика проекта, она не заменяет официальные проверки блоков 1-4.

Где мы сейчас (после M1-M4):
- Блок 1 (контракт, 25 очков): адаптер реализует все 20 тестов C01-C20 — закрытый сброс episode_dir, конверт действия {name, args}, первый и поздний 관찰, курсор list_records в виде строки, калькулятор в виде десятичной строки, submit с {accepted: true}, закрытая награда 0, лимит 60 с, изоляция truth. Оценка: 25/25.
- Блок 2 (закрытые эпизоды D01-D20, 25 очков): добавлены детерминированные настройки генератора gap_mode (partial/missing/mixed), composite_scenario (alternate/first/second/both), флаги split_payment/refund/recurring. Остаток риска: чистые эпизоды D02-D05 (разделенный платеж, возврат, повторяющиеся суммы, граница валюты/периода) флаги только разрешают/запрещают, но не гарантируют'apparition; детерминизм возможен при предварительной генерации épisodes подбором сидов или при добавлении force-флагов. Оценка: ~23/25.
- Блок 3 (матчер и награда, 25 очков): строгие соглашения — точные ID/валюта/сумма/доказательства, tau=0 по умолчанию, максимальное паросочетание с детерминированной раскадровкой, лимиты 30/10/1000, точность 1e-9, клип [-1,1], неизвестный тип — FP, а не падение. Все 20 официальных тестов + M01-M12 проходят. Оценка: 25/25.
- Блок 4 (парные проверки P01-P20, 15 очков): load_episode загружает преобразованную episode_dir, truth восстанавливается в закрытом процессе жюри, обратное отображение ID сохраняет связи. Оценка: 15/15.
- Инженерные якори (10 очков): одна команда запуска python -m letro.verify, версии кода/конфига/зависимостей, trajectories.jsonl с полями раздела 9, измеренный анализ неудач, честные ограничения. Оценка: 10/10.

Итоговая оценка до запуска жюри: примерно 93-98 из 100. При сохранении выявленных рисков (блоки D02-D05 и C18) реалистичнее 90-95.

## 3. Топ-5 рисков и блокеров

1. Официальное жюри еще не запущено против этого репозитория. Вся оценка — вывод из собственных тестов, а не сертифицированный результат. Доказательство: нет прогона жюри в этой сессии. Влияние: итоговый счет неизвестен до официального запуска. Устранение: получить harness жюри и организаторские политики, провести scored run.
2. Чистые эпизоды D02-D05 (разделенный платеж, возврат, повторяющиеся суммы, граница валюты/периода) не форсируются конфигом: флаги split_payment/refund/recurring только включают/выключают вероятностное появление (20% / 12% / 50%). Доказательство: `letro/generator/company.py`, `letro/schema.py` (флаги boolean по умолчанию true). Влияние: очки блока 2 под угрозой, если жюри генерирует épisodes samo через generate_episode с нашими настройками. Устранение: добавить force-флаги или доставить 20 предсгенерированных закрытых épisodes блока 2, отобранных подбором сидов.
3. C18: лимит 60 с включает время работы политики; адаптер запускает отсчет с reset (включая генерацию в train-режиме). На медленном машине или с медленной политикой episódios могут уходить в truncated с пустыми findings. Доказательство: `judge_adapter.py` (_deadline). Влияние: потеря очков блока 1 на слабом железе. Устранение: подтвердить опубликованные характеристики машины и бюджет времени политики.
4. Самооценка verify 100/100 не является официальной проверкой. Доказательство: `python -m letro.verify`. Влияние: может создавать ложную уверенность. Устранение: честное позиционирование в отчете (уже сделано).
5. Парные проверки P01-P20: ключ FX date:source:target не является суррогатным ID и не может быть заменен; одинаковые строки в разных таблицах не должны стать ложными связями. Доказательство: README раздел "Генератор конфигурационных ключей", `letro/generator/errors.py`. Влияние: провал парных проверок при некорректной замене. Устранение: уже структурно обработано; требуется проверка реальным harness pair checks.

## 5. Три контрольных вопроса

1. Блок 2, D02-D05: чистые épisodes с разделением платежа, возвратом, повторяющимися суммами и границей валюты/периода. Флаги split_payment/refund/recurring только разрешают/запрещают, но не гарантируют'apparition. Кто будет генерировать 20 закрытых épisodes блока 2 — команда (предсгенерированные подбором сидов) или жюри через generate_episode с нашими настройками? Почему это убивает: без детерминизма чистых scénarios теряем до 25 очков блока 2. Что должно быть в ответе: порядок формирования épisodes блока 2 и кто несет ответственность за их генерацию.
2. Блок 1, C18: лимит 60 с с момента reset включает время политики; адаптер запускает отсчет с reset (включая генерацию в train-режиме). Каковы опубликованные характеристики машины жюри и бюджет времени политики? Почему это убивает: медленное железо или медленная политика -> truncated -> пустые findings -> 0 за épisode. Что должно быть в ответе: характеристики машины и лимит времени политики.
3. Блок 4, парные проверки: после биективной замены ID ключ FX date:source:target не является суррогатным ID и не меняется; одинаковые строки в разных таблицах не становятся ложными связями. Кто ведет обратное отображение ID и проверяет соответствие truth/проведенных данных? Почему это убивает: некорректная замена ломает truth и сравнения, парные проверки проваливаются. Что должно быть в ответе: подтверждение, что жюри выполняет замену через копию episode_dir и обратное отображение, команда не реализует transform=true.
